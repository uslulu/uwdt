# Производительность UWDT на macOS arm64

## Сравнение после изменений, 18 ноября 2026 года

Apple M1, macOS 27.2, Go 1.27.1. Условия исходного замера открытого окна и параметры инструментов сохранены ниже. Новые замеры проведены без VPN и изменения системных маршрутов.

| На одинаковом потоке 2 000 INFO по 120 байт | Синхронная запись | Очередь записи |
|---|---:|---:|
| Передача всей серии, три прогона | 153,5–180,4 мс | 127,2–131,3 мс |
| p95 вызова на стороне отправителя | 13,25–33,83 мкс | 0,625–1,208 мкс |
| p99 того же вызова | 3,46–3,69 мс | 3,88–3,93 мс |

| Выделено в Go на серию | 80,2 КБ | 131,4–131,5 КБ |

Сравнивались синхронный путь, воспроизведённый в BenchmarkSessionLog, и рабочая реализация с очередью. Формат строки и период Sync одинаковы, каждые 50 записей. RSS измерена отдельно для каждого режима через /usr/bin/time -l, по три серии в одном процессе. Время передачи исключает финальный Close, RSS включает завершение процесса. Уменьшились время передачи серии и p95. При переполнении очереди важные сообщения ждут записи, p99 и пиковая RSS в этом опыте выросли. Эти числа характеризуют вызов записи, а не задержку от core до отрисовки WebView.

Для повтора собрать `go test -c ./backend -o /tmp/uwdt-bench.test`, затем запустить отдельно каждый режим, например `/usr/bin/time -l /tmp/uwdt-bench.test -test.run '^$' -test.bench 'BenchmarkSessionLog/queued' -test.benchtime 1x -test.count 3 -test.benchmem`. Второй режим — synchronous. Кэш измерен через `-test.bench BenchmarkRussianSnapshot -test.count 3 -test.benchtime 200ms -test.benchmem`. Проверка числа операций — TestRouteWatchUsesOneSnapshotForForeignHosts.

По коду запись и Sync выполняет отдельная горутина вне Bridge.mu, экспорт копирует поток, сегмент журнала ограничен 4 МиБ. Проверки подписки используют до трёх одновременных реальных запросов через Xray, отмену и кэш на две минуты. Ускорение подписки на реальных серверах не измерялось.

Исходная медиана RSS приложения вместе с WebKit при отключённом VPN составляла 97,1 МиБ. Тестовый процесс журнала с этой величиной напрямую несопоставим. Для сравнения всего приложения на стенде повторить методику ниже для обеих версий, затем для подключённого простоя и одинакового потока через TURN и Xray. Записать CPU, RSS приложения и WebKit, байты/с и потери. Для Rust AEAD подтверждена совместимость с Go в тесте. До выбора реализации нужны парные длительные прогоны с одним сервером, размером пакетов, скоростью и длительностью, включая разрывы и восстановление.

## Сборка и запуск

`npm ci` с локальным кэшем и `npm run build` прошли. Размеры сняты со свежего `dist`, который встраивается в бинарник по `main_darwin.go:17–18`. Команда Wails из CI (`.github/workflows/build.yml:77`) с пропуском уже выполненной сборки frontend и генерации bindings остановилась на compile с `exit status 1`. Прямой `go build -tags production` показал ошибку линковщика `Undefined symbols for architecture arm64: "_OBJC_CLASS_$_UTType"`. Обход через явное указание framework сработал во временной копии:

```sh
go build -buildvcs=false -tags desktop,production \
  -ldflags "-w -s -extldflags '-framework UniformTypeIdentifiers' -X pwdtt/backend.localTestVersion=1.9.2" \
  -o ../pwdtt .
```

Бинарник упакован вручную с параметрами из `build/darwin/Info.plist:4–24`, отдельным bundle ID `com.wails.uwdtaudit` и локальной ad hoc подписью. Запуск с отдельным `HOME` и `CFFIXED_USER_HOME`. Флаг `localTestVersion` отключил автостарт и фоновую проверку обновлений (`backend/app.go:42–49`). В песочнице окно не открылось из-за `SIGABRT` при вызове создания окна Wails (`main_darwin.go:35`). Вне песочницы приложение работало. Во втором таком запуске CoreGraphics обнаружил видимое окно «UWDT» шириной 900 px. В журнале присутствовало предупреждение WebKit `sandbox_extension_issue_file_to_process … Operation not permitted` для временного bundle. Готовность всего UI и сценарии кликов не проверялись.

В первом запуске после 8 с прогрева собраны 10 снимков с периодом около 1 с через `ps`. Сумма включает основной PID и три появившихся после старта PID WebKit (WebContent, Networking, GPU). WebKit запускает XPC-процессы с PPID 1, поэтому принадлежность оценена по появлению PID в момент запуска. RSS может учитывать общие страницы несколько раз. Дамп горутин и наличие окна проверены на втором запуске той же сборки. Малое окно измерений, отдельный профиль и отключённая проверка обновлений ограничивают переносимость baseline.

Подключение и нагрузка не проверены: нужен согласованный рабочий VPN-профиль для теста и интерактивное повышение прав helper, который изменяет сетевые маршруты и DNS хоста (`backend/bridge.go:63–89,197–225`, `backend/wg_darwin.go:269–294,716–825`). Текущая сборка не открывает pprof endpoint и не экспортирует профили из lifecycle приложения (`main_darwin.go:20–67`, `backend/app.go:34–62`). Для полного замера нужен изолированный стенд и диагностическая сборка с профилированием.

## Локальный микробенчмарк парсинга

Команда `go test ./tests -run '^$' -bench 'Benchmark(Obfs|ParseWG|Aggregate)' -benchmem -benchtime=200ms -count=3` выбрала три существующих сценария парсинга (`tests/benchmarks_test.go:29–65`, реализация в `backend/wg.go:236–269`). Диапазоны отражают три повтора, это измерение запуска/обработки конфигурации.

| Сценарий | нс/операцию | байт/операцию | аллокаций/операцию |
|---|---:|---:|---:|
| ParseWGConfig | 2 427–2 470 | 5 856 | 46 |
| Minimal | 1 590–1 839 | 4 752 | 24 |
| LargeAllowedIPs | 3 487–3 885 | 9 560 | 29 |

Throughput, аллокации/пакет и mutex contention не измерены. Проверка производительности под нагрузкой должна фиксировать режим VK TURN/WireGuard или Xray, число воркеров, MTU, состояние «Россия напрямую», тип нагрузки и скорость. Это позволяет сравнивать результаты без смешения путей (`backend/bridge.go:69–88,159–214`, `backend/wg_darwin.go:60–76,135–147`, `backend/excludes.go:362–376`).
